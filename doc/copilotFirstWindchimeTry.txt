## 🎵 How to map widget inputs to windchime sounds

Use the existing channel semantics from WidgetChannel.cpp:

- `position` → pitch, tube index, or strike location
- `velocity` → strike energy / loudness / damping
- `isActive` → trigger a new chime event
- `previousPosition` / `previousVelocity` → optional motion smoothing

A practical mapping for windchimes would be:

- **One widget channel = one chime tube**
- `velocity` controls **how hard the chime is struck**
- `position` controls **which resonant frequency is used**
- `isActive` triggers a note onset
- Optional motion or acceleration can add **randomized shimmer / damping**

That gives you a very natural “windchime-like” behavior without needing physical actuators.

User: Does the decay method take into account the non-linear response of human hearing?

GitHub Copilot: ## Answer

No — the current decay logic does **not** account for the non-linear response of human hearing.

### What it does now
In WindchimeAudioEngine.cpp, the note amplitude is reduced by a fixed exponential factor each sample:

- `voice.envelope *= voice.decayRate`
- `voice.decayRate` is a constant such as `0.9999f`

That means the decay is **linear in amplitude space** (exponential in time), but it does **not** translate volume into a perceptual loudness scale like dB, nor does it apply any hearing-weighting.

### Why that matters
Human hearing is approximately logarithmic, so a given reduction in amplitude does not feel like the same reduction in perceived loudness. Right now, the code is deciding “quiet” based on raw sample amplitude, not on **perceived loudness**.

### If you want hearing-aware decay
A better approach would be to decay in **dB** or apply a **loudness curve** so the tail feels natural. For example:

- compute decay as a target dB drop over time
- convert to linear amplitude for rendering
- optionally use a simple psychoacoustic curve or A-weighting

## 🔎 What I meant by “small modulation component”

I meant the **extra, very slight secondary tone** that rides on top of the main chime pitch.

### In practice
The engine adds a **second sine oscillator** that is:
- **slightly detuned** from the main note
- **lower in amplitude**
- **decayed separately** so it lingers a bit longer

In the current implementation, that is the `secondaryResonance` path in WindchimeAudioEngine.cpp. It uses:
- `secondaryResonanceGain`
- `secondaryResonancePitchRatio`
- `secondaryResonanceDecayDbPerSecond`

### Why it helps
That small detuned component makes the sound feel more like a **real metal chime** instead of a single clean tone. It adds a faint “afterglow” / metallic shimmer without making the note sound muddy.

### Current defaults
From WindchimeAudioEngine.h, the defaults are roughly:
- `secondaryResonanceGain = 0.18`
- `secondaryResonancePitchRatio = 1.03`
- `secondaryResonanceDecayDbPerSecond = 2.5`

So, in plain language: **a tiny second resonance, a little higher in pitch, mixed in at low level and faded out separately**.
